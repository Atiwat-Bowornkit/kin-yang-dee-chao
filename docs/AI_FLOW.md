# AI Flow — แอปใช้ AI ตรงไหน และตรวจอะไรเอง

แอป **ไม่ได้ฝึกหรือสร้างโมเดลเอง** ใช้โมเดลของผู้ให้บริการผ่าน API แบบ OpenAI-compatible
(`POST {baseUrl}/chat/completions`) ส่วนที่เหลือ — ตรวจผล จับคู่ จัดอันดับ อธิบาย — เป็นโค้ดในแอปที่ทดสอบได้

```text
รูป ──▶ [AI] ระบุวัตถุดิบ ──▶ [แอป] ตรวจ JSON/schema ──▶ draft
                                                       │
                       [ผู้ใช้] แก้ชื่อ / ลบ / เพิ่ม / เลือกของในครัว / ยืนยัน
                                                       ▼
                              confirmed ingredients + change set (เก็บผล AI เดิมแยกไว้)
                                                       │
            ┌──────────────────────────────────────────┴───────────────────────┐
            ▼                                                                  ▼
 [แอป] จับคู่สูตรในแอป 65 เมนู (ไม่ใช้เน็ต)                  [AI] แนะนำเมนูเพิ่ม — เฉพาะเมื่อผู้ใช้กด
 ตรวจเงื่อนไข เวลา/อุปกรณ์/ความเผ็ด                              [แอป] ตรวจแต่ละสูตร, cache ผูกกับ input
            └──────────────────────────────┬───────────────────────────────────┘
                                           ▼
                [แอป] จัดอันดับแบบคงที่ + RecommendationExplanation (ตัวเลขจริง)
```

## 1. ระบุวัตถุดิบจากรูป (`ApiService.recognizeIngredient`)

| ขั้น | รายละเอียด |
|---|---|
| ก่อนส่ง | ต้องมี key, Base URL ต้องเป็น `https://` (ยกเว้น localhost/10.0.2.2 สำหรับพัฒนา), รูป ≤ 6 MB, MIME จากไฟล์จริง |
| คำขอ | system prompt `recognize-v2` + รูป base64, `max_tokens` 4000 |
| ตรวจคำตอบ | ต้องเป็น JSON object ที่มี `ingredients` เป็น list; `finish_reason=length` = ถูกตัด → error `truncated` (ไม่ใช้ผลครึ่ง ๆ) |
| แปลงผล | ทุกรายการได้ `source = AI ตรวจพบ`; เก็บเครื่องปรุงที่ AI เห็นด้วย (ผู้ใช้ตัดสินใจเอง); สูงสุด 12 รายการ — ถ้าเกิน **แจ้งจำนวนที่ไม่ได้แสดง** ใน UI และ trace |
| ผลลัพธ์ | `ScanRecord` สถานะ `draft` (ไม่อยู่ในประวัติ, ไม่ส่งไปหาสูตร) → หน้า "ตรวจวัตถุดิบ" |

ประเภท error ที่แยกได้: ไม่มี key, ตั้งค่าผิด (404/URL), unauthorized (401/403), rate limit (429 หรือ error ใน body),
bad request (400/413/422), เครือข่าย, timeout, บริการขัดข้อง (5xx), คำตอบผิดรูปแบบ, คำตอบถูกตัด, รูปใหญ่เกิน, ยกเลิก

## 2. ขั้นตรวจและยืนยัน (ผู้ใช้)

- แก้ชื่อ (เก็บเป็น rename `จาก → เป็น`), ลบ, เพิ่มจากฐานข้อมูลหรือพิมพ์เอง (`source = เพิ่มเอง`)
- ชื่อที่ไม่อยู่ในฐานข้อมูลคงไว้ตามที่พิมพ์ — ไม่เดาให้ใกล้เคียง (ไม่ทำ fuzzy match)
- เลือก **ของพื้นฐานในครัว** (น้ำมัน น้ำปลา ฯลฯ) เอง — แอปไม่อ้างว่า AI เห็นของเหล่านี้; ค่าที่เลือกเป็นค่าเริ่มต้นครั้งถัดไป
- ยืนยันแล้ว: `status = confirmed`, `confirmedAt`, `detected` (ผล AI เดิม) ไม่ถูกเขียนทับ, `changes` = เพิ่ม/ลบ/แก้ชื่อ
- รายการจากเวอร์ชันก่อน (`legacy`) ต้องผ่านขั้นนี้ก่อนแสดงสูตร

## 3. จับคู่สูตรในแอป (`RecipeRepository.matchRecipes`)

- จับคู่ด้วย ingredient id + ชื่อพ้องแบบตรงทั้งคำ: **ปลา ≠ น้ำปลา, ไข่ไก่ ≠ ไข่เค็ม, ไก่ ≠ ไข่ไก่**
- `x/y` = วัตถุดิบหลักที่มี / วัตถุดิบหลักทั้งหมดของสูตร (ไม่นับเครื่องปรุง ไม่นับของเสริม) — **เป็นความครบของวัตถุดิบ ไม่ใช่ความมั่นใจของ AI**
- เครื่องปรุงแยกเป็น "มีในครัว" (ผู้ใช้เลือกไว้) กับ "ต้องเตรียม" (ไม่ได้เลือก)

## 4. เงื่อนไขการทำอาหาร (`CookingConditions`)

เวลา (ไม่จำกัด / ≤15 / ≤30 นาที), จำนวนที่ (1–12), อุปกรณ์ (ไม่ระบุ / ไม่มีเตา / กระทะ หม้อ ซึ้ง ไมโครเวฟ เตาอบ เครื่องปั่น), ความเผ็ด

- สูตรในแอป: ใช้กรอง — สูตรที่ไม่ผ่านถูกซ่อนหลังปุ่ม "ดูอีก N เมนูที่ไม่ตรงเงื่อนไข" (ไม่หายเงียบ)
- ข้อมูลที่ไม่มี (เช่น AI ไม่บอกเวลา/อุปกรณ์/ความเผ็ด) → แสดงว่า **ไม่ทราบ** ไม่ถือว่าผ่าน
- AI: ส่งเงื่อนไขเป็นข้อกำหนดใน prompt `recipes-v2` และขอปริมาณสำหรับจำนวนที่ที่เลือก

## 5. แนะนำเมนูจาก AI (`ApiService.suggestRecipes`) — เฉพาะเมื่อผู้ใช้กด

- ส่ง: วัตถุดิบที่ยืนยัน, ของในครัวที่เลือก, เงื่อนไข — **ไม่ส่งรูป และไม่ส่งรายการที่ยังไม่ยืนยัน**
- ตรวจทีละสูตร: ต้องมีชื่อ, ส่วนผสมที่ใช้ได้ ≥ 2, ขั้นตอน ≥ 2; ตัวเลขนอกช่วงถูกทิ้ง; เวลาไม่ระบุ = ไม่ทราบ; ไม่ใช้ kcal ที่ AI เดา
- สูตรที่ไม่ผ่านถูกนับและบอกเหตุผลใน trace; ไม่เติมสูตรปลอมให้ครบ 3 และตัดส่วนเกิน 3
- **Cache key** = prompt version + โมเดล + endpoint + วัตถุดิบ (เรียงแล้ว) + ของในครัว + เงื่อนไข
  - key ตรง → แสดง "ผลที่บันทึกไว้ (…ที่แล้ว)" ไม่เรียก AI ซ้ำ ใช้ได้ออฟไลน์
  - key ไม่ตรง (แก้วัตถุดิบ/เงื่อนไข/โมเดล) → แสดงเป็น "ผลเก่า" พร้อมปุ่มขอใหม่
- เปลี่ยนเงื่อนไขระหว่างรอ → ยกเลิกคำขอเดิม และทิ้งคำตอบที่มาช้า

## 6. จัดอันดับและคำอธิบาย (`rankRecommendations`, `RecommendationExplanation`)

ลำดับคงที่และอธิบายได้:
1. ไม่ผ่านเงื่อนไขน้อยข้อก่อน
2. ความครบของวัตถุดิบหลัก (x/y) มากก่อน
3. ของสำคัญที่ขาดน้อยก่อน
4. ข้อที่ตรวจไม่ได้ (ไม่ทราบ) น้อยก่อน
5. ใช้เวลาน้อยก่อน (ไม่ทราบเวลาอยู่หลัง)
6. id ของสูตร (ให้ผลเหมือนเดิมทุกครั้ง)

คำอธิบายในหน้าสูตร: "มีวัตถุดิบหลัก x/y อย่าง", มีแล้ว / ต้องเตรียมเพิ่ม / ของเสริม / ของในครัว, ผลแต่ละเงื่อนไข, แหล่งสูตร

## 7. Trace และความเป็นส่วนตัว (`AiTrace`)

แต่ละคำขอเก็บ (สูงสุด 6 รายการต่อการสแกน): request id, ชนิด, เวลาเริ่ม, ระยะเวลา, endpoint (scheme+host+path เท่านั้น), โมเดล,
prompt version, สรุป input (เช่น "image/png 135 KB"), HTTP status, finish_reason, ผลตรวจ, หมายเหตุ, ตัวอย่างคำตอบ ≤1500 ตัวอักษร

`sanitizeForTrace` ลบ: key ของผู้ใช้, `Bearer …`, สตริงหน้าตาเหมือน key (`sk-…` ฯลฯ), รูป base64 — แสดงในโหมดสาธิตเท่านั้น
log ของแอปบันทึกแค่ชนิดเหตุการณ์/สถานะ ไม่บันทึก key, header หรือเนื้อหาคำขอ

## 8. Key

ลำดับการเลือก: key ที่ผู้ใช้ใส่ (เก็บใน `flutter_secure_storage` / Android Keystore) → key ที่ฝังตอน build (`--dart-define`, สำหรับนักพัฒนา) → ไม่มี
ผลทดสอบการเชื่อมต่อผูกกับ fingerprint (hash) ของ key+URL+โมเดล — เปลี่ยนค่าแล้วสถานะกลับเป็น "ยังไม่ได้ทดสอบ"
